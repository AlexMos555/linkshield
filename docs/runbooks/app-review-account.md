# Аккаунт для проверяющих магазинов (App Store, Google Play, RuStore)

Вход в Cleanway — по коду из письма. Проверяющим магазинов мы даём свой
адрес, и код уходит на него, а не к ним: проверяющий не может войти и
отклоняет сборку или ставит её на паузу. Поэтому есть **один аккаунт
`review@cleanway.ai` с длинным случайным паролем**. Приложение показывает
поле пароля **только** когда введённый адрес точно совпадает с адресом из
списка сборки `EXPO_PUBLIC_REVIEW_EMAILS`; у всех остальных вход по коду
остаётся прежним — то же поле, та же кнопка «Отправить код», тот же запрос.

Где что лежит:

| Что | Где |
|---|---|
| Список адресов в сборке | `mobile/eas.json` (профили `preview` и `production`); для локальных Android-сборок — `mobile/.env` или `export` в `docs/RUSTORE_SUBMISSION.md` §2 |
| Логика на экране входа | `mobile/src/utils/review-login.ts`, `mobile/app/auth.tsx`; тесты — `mobile/scripts/test-auth-error-key.mjs` |
| Создать аккаунт / сменить пароль | `python3 scripts/create_review_account.py` (тесты — `tests/test_create_review_account.py`) |
| Пароль | **только** в связке ключей macOS (служба `Cleanway app review account`, учётная запись `review@cleanway.ai`) и в полях для проверяющих в трёх консолях. Не в git, не в `.env`, не в чате |

## Когда заработает

Со **следующей** мобильной сборкой (версии в этом изменении не поднимались).
Уже собранные APK, AAB и IPA поля пароля не имеют — для них в заметках
остаётся «вход необязателен». iPhone: обычная сборка EAS `production` —
переменная уже в `eas.json`. Android (RuStore, Google Play) собирается
локально: переменная экспортируется в рецепте `docs/RUSTORE_SUBMISSION.md` §2.

## Создать аккаунт или сменить пароль (5 минут)

Запускаете вы, на своём Mac. В корневом `.env` должны быть `SUPABASE_URL` и
`SUPABASE_SECRET_KEY` (или старый `SUPABASE_SERVICE_KEY`) — те же, что у сервера.

1. Посмотреть, что будет сделано (ничего не записывает):
   ```bash
   python3 scripts/create_review_account.py --dry-run
   ```
   Ждём «создал бы review@cleanway.ai» (первый раз) или «сменил бы пароль … (id …)».
2. Сделать:
   ```bash
   python3 scripts/create_review_account.py
   ```
   Скрипт создаёт пользователя с подтверждённым адресом (или меняет пароль
   существующему и снимает блокировку), кладёт пароль в связку ключей и
   проверяет, что он там. На экран пароль не выводится никогда.
3. Скопировать пароль в буфер обмена:
   ```bash
   security find-generic-password -s 'Cleanway app review account' -a review@cleanway.ai -w | tr -d '\n' | pbcopy
   ```
   Посмотреть его глазами — приложение «Связка ключей» → поиск
   «Cleanway app review account».
4. Вставить адрес и пароль во все три консоли (ниже) и сохранить.

**Сменить пароль = запустить скрипт ещё раз.** Старый пароль перестаёт
работать сразу, поэтому после смены обновите его во всех трёх консолях.
Менять: если пароль мог попасть не туда, и перед проверкой, если аккаунт был
заблокирован (повторный запуск снимает блокировку).

Если скрипт закончился `keychain error` — пароль в Supabase уже сменён, но не
сохранён: просто запустите его ещё раз. `config error` — проблема в `.env`
(названия переменных в сообщении) или адрес не аккаунт для проверяющих (ниже,
«Почему это безопасно»); запросов в Supabase в этом случае не было.
`api error` — ответ Supabase (код и причина в сообщении, без пароля).

## Куда вставить

| Магазин | Где | Что |
|---|---|---|
| App Store | App Store Connect → приложение → версия → **App Review Information** → включить **Sign-in required** | User name `review@cleanway.ai`, Password — из связки ключей. Заметки — `docs/IOS.md` §3.6 |
| Google Play | Play Console → **App content → App access** → «All or some functionality in my app is restricted» → Add instructions | Поля и текст — `docs/STORE_SUBMISSION_KIT.md` §1.5. Галочку «Allow Android to use the credentials … for testing» **не** ставить (ниже — почему) |
| RuStore | Консоль RuStore → версия → комментарий для модератора | Заметка из `docs/RUSTORE_SUBMISSION.md` §5 плюс адрес и пароль |

## Что видит проверяющий

Настройки → «Войти» → поле почты. Вводит `review@cleanway.ai` — подзаголовок
меняется на «Для этого аккаунта вход по паролю.», появляется поле «Пароль»,
кнопка «Войти». Дальше — как после входа по коду: экран аккаунта, устройства.
Письмо не отправляется. Любой другой адрес — всё как раньше: «Отправить код».

Ошибки: неверный пароль — «Неверный адрес или пароль.»; много попыток подряд —
«Слишком много попыток входа…»; нет сети — «Нет соединения…».

Бесплатный аккаунт привязывает 2 устройства (`FREE_ACCOUNT_DEVICE_LIMIT`).
Третье устройство проверяющего попадёт на экран аккаунта с предложением
отвязать одно из прежних — это нормально. Если устройства прошлых проверок
мешают, войдите этим аккаунтом на своём телефоне → «Аккаунт» → отвяжите их →
выйдите.

Apple проверяет, что аккаунт можно удалить, и проверяющий иногда правда его
удаляет. Тогда следующий вход не сработает: **запустите скрипт ещё раз** — он
создаст аккаунт заново — и обновите пароль в консолях.

## Отключить

- **Между проверками:** Supabase → Authentication → Users → `review@cleanway.ai`
  → **Ban user**. Пароль перестаёт работать сразу (проверяющий увидит «Что-то
  пошло не так»). Включить обратно — запустить скрипт (новый пароль, блокировка
  снята) и обновить пароль в консолях.
- **Насовсем:** убрать адрес из `EXPO_PUBLIC_REVIEW_EMAILS` (`mobile/eas.json`;
  для Android — `export` в `docs/RUSTORE_SUBMISSION.md` §2 и `mobile/.env`) в
  следующей сборке — поле пароля пропадёт — **и** заблокировать или удалить
  пользователя. Одного удаления из сборки мало: пароль по-прежнему работает
  через API Supabase для того, кто его знает.

## Почему это безопасно

- **Скрытое поле — не защита, а удобство.** Вход по паролю в Supabase
  (`POST /auth/v1/token?grant_type=password`) открыт любому, у кого есть
  публичный ключ приложения. Защищает аккаунт сам пароль: 32 случайных буквы и
  цифры (модуль `secrets`, ≈190 бит) — подобрать нельзя. Он проходит правила
  проекта (`scripts/supabase_mail.py`: `password_min_length`,
  `password_required_characters`, проверка по утечкам HIBP).
- **Перебор режет Supabase.** `/auth/v1/token` ограничен по IP: по умолчанию
  150 запросов за 5 минут, всплеск до 30 (Supabase → Authentication → Rate
  Limits, строка про токены; в Management API — `rate_limit_token_refresh`).
  Тот же счётчик обслуживает обновление сессий всех пользователей, поэтому
  сильно его не занижать. Лимиты, которыми управляет `scripts/supabase_mail.py`
  (`rate_limit_verify` = 10 — проверка кодов, `rate_limit_email_sent` —
  письма), к паролю не относятся. Когда в Supabase включат капчу, вход по
  паролю тоже её потребует — приложение решает её по запросу, как и для кода.
- **Чужие аккаунты так не открыть.** Кто зарегистрировался по коду, у того нет
  пароля — вход по паролю к его аккаунту не подходит, есть адрес в списке или
  нет. Экран к тому же отказывает в пароле любому адресу не из списка ещё до
  запроса.
- **В списке — только наши адреса.** Приложение само выбрасывает из
  `EXPO_PUBLIC_REVIEW_EMAILS` любой адрес не на `@cleanway.ai`
  (`parseReviewEmails` в `mobile/src/utils/review-login.ts`) — откуда бы ни
  пришла переменная: `eas.json`, `mobile/.env` или `export` из
  `docs/RUSTORE_SUBMISSION.md` §2. Опечатка или вставленный личный адрес не
  покажут настоящему человеку поле пароля. Тест
  (`mobile/scripts/test-auth-error-key.mjs`) это закрепляет и, кроме того,
  падает, если в профиле `eas.json` есть адрес, который приложение выбросило бы.
- **Скрипт не трогает чужие аккаунты.** `create_review_account.py` отказывает
  (`config error`, ни одного запроса — и в `--dry-run` тоже) любому адресу,
  который не на `@cleanway.ai` или которого нет в `EXPO_PUBLIC_REVIEW_EMAILS`
  профиля `production` в `mobile/eas.json`. Иначе опечатка в `--email` дала бы
  настоящему человеку пароль, который знает только ваша связка ключей,
  подтвердила бы его адрес, сняла бы блокировку и разлогинила бы его на всех
  устройствах.
- **В аккаунте нет настоящих данных.** Только бесплатный тариф: не оформлять
  на него подписку и не выдавать план вручную, не создавать семью, не держать
  в нём свои устройства и ничего личного; пользоваться им только для проверок.
  Всё, что в нём есть, видят проверяющие трёх магазинов.
- **Почта ему не нужна.** Адрес подтверждается при создании (через API, без
  письма), приложение ему писем не шлёт. Отдельного ящика или правила в
  Cloudflare Email Routing не требуется.
- **Автотесты Google без пароля.** Галочка в Play «Allow Android to use the
  credentials … for testing» отдала бы пароль роботу pre-launch report: он
  ходит по всем экранам на десятках устройств, упрётся в лимит устройств и
  может нажать «Удалить аккаунт». Поэтому — не ставить.
