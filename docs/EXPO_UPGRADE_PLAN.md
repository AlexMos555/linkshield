# План обновления Expo SDK: 54 → 58

Для основателя. Это только оценка: код не менялся, в этом PR один документ.
Опытный прыжок на SDK 58 уже сделан в черновом PR
[#253](https://github.com/AlexMos555/linkshield/pull/253) (`exp/expo-sdk-58`,
коммит `46c4f7a`, «do not merge»). Здесь разобрано, что он доказал, чего не
доказал и как довести обновление до релиза.

Все внешние источники открыты и перепроверены **24 октября 2026**; ссылки в
конце. Факты о нашем коде даны со ссылками на файлы в `main` (`4806479`).

### 1.2 Безопасность

По `mobile/package-lock.json` в Dependabot сейчас четыре отклонённых
предупреждения (`tolerable_risk`) по трём пакетам. Те же пакеты в корневом lock
отклонены как #17–#20.

| Предупреждение | Откуда | Попадает ли в приложение | После #253 |
|---|---|---|---|
| #6 `decode-uri-component` (CVE-2026-45822, отказ в обслуживании на испорченном `%`-кодировании) | `query-string` внутри `expo-router` | **Да.** Им разбираются ссылки `cleanway://`, а такую ссылку может открыть любое приложение или сайт | Исчезло: `expo-router` больше не использует `query-string` |
| #7, #8 `image-size` (зацикливание на JXL/HEIF/ICNS) | Metro (сборщик) | Нет, только во время сборки | Исчезло (Metro 0.87) |
| #9 `node-forge` (проверка подписи RSA) | `@expo/cli` → `@expo/code-signing-certificates` | Нет, только CLI | Осталось: исправленной версии нет |

`npm audit` в #253: 53 → 37 записей. Ещё #253 разблокирует Dependabot-обновления,
которые не встают на SDK 54: `@sentry/react-native` 7.2 → 8.28 и `react-dom`
(теперь 19.3.0 вместе с `react`).

#### Дыра, о которой Dependabot не предупредит: `expo-share-intent` на Android

**Что это.** Обход пути («Dirty Stream», CWE-22) во всех выпущенных версиях
2.0.0–8.0.0. У нас 5.1.1: и в `main`, и в lock зеркала. Записи в базе GitHub
Advisory нет (проверено 24.10.2026), поэтому Dependabot и `npm audit` молчат.
**Закрыто в #318** патчем для 5.1.1 (ниже, «Что сделано»).

**Как работает.** Когда в Cleanway «делятся» файлом, модуль копирует его в
`cacheDir` под тем именем, которое сообщил ContentProvider отправителя
(`_display_name`), и никак его не проверяет. В `getDataColumn`
(`android/.../ExpoShareIntentModule.kt`) стоит
`targetFile = File(context.cacheDir, fileName)`. Имя вида
`../shared_prefs/…` выводит запись за пределы кэша, в остальную приватную
папку Cleanway.

Для этого хватает одного `ACTION_SEND` с `EXTRA_STREAM` и любым типом, кроме
`text/plain`. Например, `text/html`: под наш фильтр `text/*` он подходит.
Копирование делает нативный код, ещё до нашего JS:

- при `OnNewIntent`, если приложение запущено (`MainActivity` в режиме `singleTask`);
- при `getShareIntent`, если это холодный старт. `ShareIntentProvider` вызывает
  его каждый раз, когда приложение становится активным.

**Чем грозит.** Вредное приложение на том же телефоне может подменить настройки,
базы и файлы списков. Например, внести мошеннический домен в «не мошенники»
или выключить защиту. Для антифишингового приложения это способ незаметно
обойти защиту. Отправителю не нужны разрешения, а пользователю не нужно выбирать
Cleanway в меню «Поделиться»: `MainActivity` экспортирована (`exported="true"`
в шаблоне), а явный интент Android доставляет в неё независимо от фильтров.
iPhone не затронут: уязвимый код есть только в Kotlin-части.

**Где исправлено.** В 8.0.1 (PR
[achorein/expo-share-intent#221](https://github.com/achorein/expo-share-intent/pull/221),
10.07.2026): имя обрезается до последней части пути, и проверяется, что файл
остаётся внутри `cacheDir`. В 9.0.0 исправление тоже есть (проверено по
исходнику пакета). 8.0.1 требует SDK 57, 9.0.0 — SDK 58. Исправления для 5.x
нет.

**Что сделано (#318, входит в 1.0.6).** На Android 1.0.6 ещё не
опубликована, поэтому отдельная 1.0.x не нужна. Ту же правку держим в ветке
`release/1.0.x`, когда она появится (риск 9).

- **Закрывает дыру** `mobile/patches/expo-share-intent+5.1.1.patch`. Это
  правка из #221 без изменений: одна строка заменена восемью. Весь
  `ExpoShareIntentModule.kt` в 5.1.1 и 8.0.0 совпадает побайтно (git blob
  `0153c89`), поэтому правка ложится как есть. После патча файл побайтно равен
  файлу из 8.0.1 и 9.0.0 (`ff5b100`). Даже строку `}                }` с двумя
  скобками оставили как у апстрима, чтобы это совпадение сохранилось.
  Применяет патч `scripts/apply-patches.js` при каждом `npm install`: в монорепо
  он ложится в общий `node_modules` в корне, в зеркале — в `node_modules`
  зеркала (проверено по рецепту `docs/RUSTORE_SUBMISSION.md` §2).
- **Сломанный патч больше не проходит молча.** Сам `patch-package` падает
  только на CI: в зеркале обычный `npm install` печатал ошибку, выходил с 0 и
  собирал код без исправления (проверено). Теперь `apply-patches.js` передаёт
  `--error-on-fail`, и установка падает везде.
- **Release без исправления не собирается.** Упавшей установки мало. Зеркало
  хранит `node_modules` между запусками, поэтому после неё там остаётся
  старый файл без исправления, а `npm install --ignore-scripts` патч вовсе
  пропускает. Ни `expo prebuild`, ни gradle исходник Kotlin не проверяют, и
  подписанный APK с дырой собирался бы как обычно (это показала проверка
  зеркала по рецепту на ревью #318). Поэтому
  `plugins/withShareIntentGuard.js`, как и защита от сборки без стартового
  списка (`withSeedGuard.js`), добавляет в `android/app/build.gradle`
  проверку. Каждая не-debug задача `pre<Variant>Build` до компиляции
  запускает
  `node scripts/check-share-intent.mjs --manifest=<AndroidManifest.xml этого android/>`,
  и если проверка не прошла, сборка падает. Отключить проверку нельзя.
  Проверено в зеркале: с исправлением `:app:preReleaseBuild` проходит;
  с непропатченным 5.1.1 в `node_modules` или с `text/*` в манифесте падает,
  и `assembleRelease` на этом останавливается, не начав компилировать
  приложение; задача выполняется при каждой сборке, а не только при первой;
  debug-сборку проверка не трогает.
- **Сужает поверхность** `androidIntentFilters` в `app.json`: `["text/*"]` →
  `["text/plain"]`. Приложение читает из «Поделиться» только `text` и `webUrl`
  (`ShareIntentRouter` в `app/_layout.tsx`), а `text/plain` в 5.1.1 идёт по
  текстовой ветке, без копирования файла. Остальные `text/*` (HTML и т. п.) и
  раньше уходили в файловую ветку и приложением не показывались: из меню
  «Поделиться» Cleanway пропадает только там, где он и так ничего не делал.
  Одного сужения мало: явный интент фильтры обходит.
- **Проверка** `mobile/scripts/check-share-intent.mjs`. CI запускает её из
  `plugins/__tests__/plugins.test.js`, зеркало — сразу после `npm install`,
  release-сборка — перед компиляцией (`withShareIntentGuard.js`). Что она
  проверяет:
  - в установленном Kotlin-коде нет `File(context.cacheDir, fileName)`;
  - имя обрезается до последней части пути, и файл принимается, только если
    его канонический путь внутри `cacheDir`;
  - в кэш нельзя записать под другим именем;
  - ниже 8.0.1 патч для установленной версии есть и применился чисто: файл
    равен результату патча, то есть файлу из 8.0.1;
  - с 8.0.1 и выше патча `expo-share-intent` не осталось;
  - у `MainActivity` один `SEND`, только для `text/plain`. Это проверяется по
    манифесту, который из `app.json` генерирует сам плагин;
  - с `--manifest=<путь>` (так её запускает release-сборка) то же самое
    проверяется в `AndroidManifest.xml`, из которого собирается этот
    `android/`. Так ловится `android/`, сгенерированный до сужения фильтра.

  `plugins.test.js` проверяет и обратное: скрипт падает на непропатченном
  5.1.1 (его собирают из патча в обратную сторону, и он побайтно равен 5.1.1),
  на 9.0.0 с забытым патчем и на манифесте с `text/*`.
- **Файлы 1.0.6 (107), собранные до слияния #318, выкладывать нельзя.**
  24.10.2026 в 00:29–00:33, до коммитов #318, собраны
  `cleanway-1.0.6-107-arm.apk` и `cleanway-1.0.6-107-rustore.apk`, к ним
  `SHA256SUMS-1.0.6.txt` (`9ae6396b…` и `bdb2ce33…`). В них непропатченный
  5.1.1: `aapt2` показывает у `MainActivity` фильтр `SEND` с `text/*`. Имена
  ровно те, что `docs/RUSTORE_SUBMISSION.md` §2 велит выкладывать, и
  versionCode тот же, 107. По версии исправленную 1.0.6 от неисправленной не
  отличить, а CHANGELOG уже обещает исправление. Поэтому:
  - удалить все файлы 1.0.6/107, собранные до слияния #318: APK, AAB и
    `SHA256SUMS-1.0.6.txt`;
  - пересобрать сайт, RuStore и Play AAB из `main` после слияния #318 по
    `docs/RUSTORE_SUBMISSION.md` §2. Заново посчитать `SHA256SUMS-1.0.6.txt`;
    `NEXT_PUBLIC_APK_SHA256` для сайта тоже берётся из нового файла;
  - перед выкладкой проверить каждый APK:
    `aapt2 dump xmltree --file AndroidManifest.xml <apk> | grep mimeType`
    должен показать `text/plain` и ни одного `text/*`. Строка `*/*` относится
    к `<queries>`, это не фильтр, она была и раньше.
- **Осталось основателю:** при проверке 1.0.6 на телефоне поделиться в Cleanway
  ссылкой из Chrome и текстом из мессенджера. Обе проверки должны открываться,
  как раньше. Без телефона проверен манифест: `expo prebuild` даёт у
  `MainActivity` один фильтр `SEND` с `text/plain`, `cleanway://` и `MAIN`
  на месте.

**В 1.1.0:** `expo-share-intent` ≥ 9.0.0, а наш патч для 5.1.1 удалить. Сам
`patch-package` на 9.0.x счёл бы его «уже применённым», потому что в 9.0.0 то
же исправление, и только предупредил бы о другой версии. Поэтому забытый патч
ловит `check-share-intent.mjs`.

### 2.2 Путь: один прыжок или по шагам

Expo советует обновляться последовательно: «We recommend upgrading SDK
versions incrementally, one at a time». #253 показал, что прыжок 54 → 58 одной
командой (`npx expo install expo@^58 --fix`) даёт согласованные зависимости и
зелёный CI. Но работу приложения на телефоне он не проверял. Предлагаем средний
путь:

1. **Шаг А — новая архитектура на SDK 54** (контрольная точка, пользователям не
   выпускается). Это самое большое изменение в поведении: через новую
   архитектуру начнут работать все наши нативные модули, события VPN, поиск
   модуля RevenueCat, `react-native-get-random-values` и передача ссылок из
   «Поделиться». На SDK 54 это можно собрать и проверить на этом iMac:
   iOS-симулятор (Xcode 26.3) и Android. Что меняется:

### 3.2 Наши config-плагины (`mobile/plugins/`)

Главный риск здесь — не ошибка сборки, а молчаливый пропуск. Четыре
Android-плагина меняют `android/app/build.gradle` и, если не находят свой якорь
(или файл не на Groovy), **тихо ничего не делают**. Сборка при этом пишет
BUILD SUCCESSFUL. Мы так и задумывали — чтобы плагин не мог сломать сборку. Но
при смене шаблона это обернётся release-сборкой с ключом отладки (её не примет
ни один магазин, и поверх неё нельзя поставить обновление), без стартового

### 6.2 Проверка руками (основатель, около 2 часов на платформу)

**Android:**

1. Установка **поверх 1.0.6** тем же ключом: нет «Приложение не установлено».

5. «Поделиться» ссылкой и текстом из другого приложения → экран проверки.

   - сборки для сайта и RuStore — то, что положено им.

    ключи семьи берутся из SecureStore, и модуль не вызывается.
    - Вход → экран «Аккаунт»: этот телефон в списке устройств отмечен как
      текущий. Id устройства создаётся через этот модуль.
    - «Семья»: создать семью или принять приглашение, чтобы сгенерировалась

      Claude собирает development-сборку с временной локальной правкой
      `src/utils/otp-request.ts` (первый ответ считается `captcha_failed`; в
      коммит не идёт), основатель входит по коду. Окно капчи должно открыться,
      nonce вернуться через `cleanway://captcha-return`, вход завершиться.
      Пока капча на сервере выключена, GoTrue токен просто игнорирует.

## 8. Когда выпускать

1. **Сейчас.** 1.0.6 тестируется и уходит в магазины. Обновление делаем только
   в ветке. PR обновления остаётся черновиком, пока 1.0.6 не раскатана на 100%
   во всех магазинах: `main` должен оставаться пригодным для срочных правок 1.0.6.
2. **Ноябрь 2026,** сразу после 1.0.6: шаги А и Б1–Б3.
3. **Конец ноября:** проверка на телефонах — внутренний трек Play, TestFlight
   internal, APK вручную.
4. **Первая половина декабря 2026 — 1.1.0:**
   - Play: поэтапная раскатка 10% → 50% → 100% за неделю;
   - App Store: фазовый выпуск;
   - RuStore;
   - APK на сайте и баннер обновления (`MOBILE_LATEST_VERSION_*` в Railway) —
     последними, через несколько дней.

   В конце декабря App Review обычно работает медленнее. Если к середине
   декабря не готовы — переносим на январь.
5. **Крайний срок подачи iOS-версии на SDK 58 — 1 марта 2027,** с запасом до
   апрельского правила Apple.
6. До 100% раскатки 1.1.0 держим ветку `release/1.0.x` на SDK 54 для срочных
   исправлений.
7. **Следующее окно — лето 2027:** SDK 59 или новее. Это до вероятного
   требования targetSdk 37 (~август 2027) и до конца поддержки SDK 58 (~осень
   2027).
